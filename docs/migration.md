# 从旧表升级

本次是领域模型变更，不能通过几次字段重命名恢复缺失的业务事实。旧库既没有 Service / 系统目录，也没有 API 输入输出契约；旧工具配置可被覆盖，调用记录只保存路径模板和少数结果字段。因此不得把当前 Tool 配置冒充历史执行时的定义，也不能从日志推造缺失的请求与响应。

## 新库

直接启动应用即可创建当前 `schema.sql` 的 17 张表。先配置 CMDB 团队归属，再在界面依次注册 Service、系统（CMDB Role）、API Tool 契约和 Workflow。示例：Commerce Service → orders_web / orders_batch / orders_kafka 等系统；系统类型不能从 Role 名称可靠推导，需要显式选择。

## 已有旧库

1. 停止所有旧应用实例，并备份数据库；H2 需在停止进程后备份完整数据文件，PostgreSQL 使用现有数据库备份流程。
2. 在数据库副本上启动新版，验证归档。启动参数额外增加 `--prodaccess.migrate-legacy=true`。这一步创建新表，并在一个事务内将 `tools`、`tasks`、`task_versions`、`runs`、`run_events`、`tool_call_audit` 原始记录复制到 `legacy_archive`；原始表保持不变。
3. 对比各旧表与归档的记录数量；在界面的 Legacy audit 按执行 ID 检查旧执行、日志及调用记录。完成标记位于 `settings['legacy_archive_v1']`，重复启动不会重复复制。原有 `audit_log`、`settings` 直接沿用。
4. 从旧定义逐一确认 Service → CMDB Role 的真实归属和系统类型，补齐 API 输入 / 输出契约后注册新 Tool；将旧脚本保存为新 Workflow 版本，形成明确的依赖绑定。旧脚本可从 Legacy audit 的 Workflow versions 中读取。
5. 用一个受控执行确认输入、Action、Tool Invocation、实际 HTTP 请求和输出记录完整，再切换到正式库。正式归档期间也只启动一个新版实例，完成后去掉迁移开关并恢复部署规模。

检测到非空旧表且尚未归档时，应用会拒绝启动并给出归档参数，避免将旧记录静默隐藏在空的新目录后。归档成功后，新 Workflow 与新执行使用全新表；旧执行继续在归档中作为原始证据查询，不会被自动重新执行或被补写为完整新审计。旧定义的自动重新发布被有意排除，因为真实 Service 归属和 API 契约需要业务确认。

旧的 `QUEUED` / `RUNNING` 状态只作为原始记录保留；升级不会继续执行它们。必须在停止旧实例后核对远端操作结果，再通过新版明确发起新的执行。

## 回退

归档流程没有删除或修改旧业务表，可以恢复备份并使用旧版本。切回前先停止新版；新版执行产生的生产数据变更不会随数据库代码回退而自动撤销。归档后的旧表保持只读；不要同时运行旧版写入旧表，否则完成标记之后新增的旧记录不会自动进入归档。

自动化测试在 H2 PostgreSQL 模式下覆盖归档开关、原始记录保留、按执行检索和重复启动。另在独立的 PostgreSQL 18.6 实例上验证过相同的升级流程。正式升级前请用实际数据库的副本演练。
